# Grok Web Build 式混合回显设计

日期：2026-08-23  
仓库：`grok-web`  
状态：设计已获用户确认，待用户复核规格文件

## 目标

解决 Grok Web 工作过程中回显信息少的问题，使浏览器端更接近 Grok Build 的过程可见性，同时保留 Web 端对长输出、历史会话和大文件的性能保护。

默认采用混合式回显：

- 工作进行中：完整显示工具调用、输入、增量输出、完成状态和耗时。
- thinking：默认折叠，用户可以单独展开查看。
- 工作完成后：过程收成摘要，点击一次摘要展开整个工具过程。
- 不复制 Grok Build 的终端外壳，也不新增一套独立事件协议。

## 现状与根因

ACP/SSE 事件和实时工具结果已经存在，问题主要发生在渲染层：

1. `MessageView.tsx` 的流式渲染只保留最后一个工具调用，前序工具卡被隐藏。
2. 工具卡默认折叠，因此实时工具结果虽然在 `liveToolResults` 中，用户默认看不到。
3. `ChatWindow.tsx` 在一轮完成后将过程消息放进摘要组；摘要展开后，工具详情仍然需要二次点击。
4. 现有延迟 thinking、延迟 tool result、大消息保护和 diff 展示是有意的性能边界，应继续保留。

## 方案边界

### 包含

- 流式阶段保留同一轮中的全部工具调用时间线。
- 流式工具卡默认展开，显示输入、增量结果或最终结果、成功/失败状态和耗时。
- 完成后的过程摘要支持一次展开全部工具卡。
- thinking 在流式和完成后的默认状态都保持折叠。
- 通过现有消息结构、`liveToolResults` 和 ACP/SSE 事件完成，不改后端协议。
- 增加覆盖多工具流式过程、实时结果可见性和完成后摘要展开的测试。

### 不包含

- 复制 Grok Build 的 TUI、ANSI 终端布局或 alternate screen。
- 新增事件总线、数据库、过程回放服务或独立日志协议。
- 默认永久展开所有 thinking。
- 移除大消息保护、延迟加载、diff 渲染限制或历史消息分页。
- 重写消息数据模型或 ACP 适配层。

## 交互设计

### 流式工作态

`ChatWindow` 继续渲染当前 `streamState.streamingMessage`，但 `MessageView` 不再过滤掉前序工具调用。每一个工具调用都按事件到达顺序保留。

工具卡在流式状态默认展开：

- 标题显示稳定工具名、输入摘要、运行/成功/失败图标和耗时。
- 内容显示命令、路径或结构化输入的现有安全摘要。
- 工具结果一到达就显示 stdout、错误文本或 diff。
- 工具仍在生成输入时显示现有的输入生成状态。
- 多个工具并行或串行时，均保留在同一条过程时间线上。

thinking 不随工具卡策略展开，继续由用户点击标题查看。这样可以提高操作可见性，同时避免把可能很长的思考文本持续铺满页面。

### 完成态

一轮过程仍使用现有 `ProcessDetailsGroup` 摘要，摘要内容继续显示状态、消息数量和工具调用数量。

点击摘要后：

- 一次挂载该过程组的所有消息和工具卡。
- 工具卡默认展开，直接可见输入和结果。
- thinking 仍默认折叠，用户可单独打开。
- 现有文件写入列表、错误、耗时、复制和 diff 展示保持不变。

再次点击摘要收起整个过程组，不改变消息数据或历史记录。

### 失败、停止和大输出

- 工具失败继续使用现有错误颜色和错误结果展示。
- 用户停止或模型错误继续使用现有状态消息，不新增特殊回显分支。
- 超大 markdown、thinking 和 tool result 继续使用现有延迟/原文保护，不因默认展开工具而绕过上限。
- 历史消息仍按现有分页加载，展开过程只在用户明确点击后触发。

## 实现结构

### `components/MessageView.tsx`

- 移除流式阶段“只保留最后一个工具调用”的显示过滤。
- 将工具详情默认展开策略与 thinking 默认展开策略分离，避免过程组展开时意外展开 thinking。
- 流式工具调用使用工具默认展开策略；完成态过程组向工具卡传递一次性展开策略。
- 保留现有工具输入摘要、延迟结果加载、diff 解析和大消息保护。

### `components/ChatWindow.tsx`

- 过程组展开时向子消息传递“工具详情展开”的显示参数。
- 不改变消息分组、历史分页、滚动锚点或 SSE 消费逻辑。
- 移除仅为流式隐藏前序工具而存在的 UI 依赖；运行状态摘要仍可保留为轻量状态提示，但不替代工具时间线。

### 测试

优先复用现有测试工具和消息夹具，新增最小断言：

1. 流式 assistant 消息包含两个或更多工具调用时，渲染结果包含所有工具名，而不是只包含最后一个。
2. 流式工具已有 `liveToolResults` 时，结果文本默认出现在渲染结果中。
3. thinking 默认不展开，工具默认展开策略不会改变这一点。
4. 完成态过程组展开后，工具输入和结果可见；过程组未展开时仍只有摘要。
5. 既有大消息、延迟 tool result、diff、错误和历史消息测试保持通过。

## 数据流

```text
ACP session/update
        ↓
现有 agent event wire / liveToolResults
        ↓
useAgentSession streamState
        ↓
ChatWindow 分组与流式消息选择
        ↓
MessageView 工具时间线 + ProcessDetailsGroup
```

本次变更不添加持久化字段，不改变 SSE 事件名称，不改变会话文件格式。

## 性能与安全

- 流式阶段会增加工具卡 DOM 数量，但只覆盖当前活动回合；完成后的历史过程仍由摘要组控制。
- 继续使用现有 `MAX_MARKDOWN_CHARS`、thinking/tool result 延迟加载和结果缓存。
- 工具输入继续走现有规范化和预览函数，不直接将任意原始对象作为主要文案输出。
- 不新增 HTML 注入路径；命令、路径和 stdout 继续由 React 文本节点渲染。

## 验收标准

- 一次包含多个工具调用的真实或 ACP 夹具回合中，流式页面能同时看到已发生的工具，而不是只显示最后一个。
- 工具结果在流式阶段无需额外点击即可看到。
- thinking 默认折叠。
- 回合完成后页面恢复为紧凑摘要；点击摘要一次能看到全部工具输入和结果。
- 工具失败、停止、超大输出、延迟历史结果和 diff 的既有行为不回归。
- 相关单元测试通过，类型检查和项目测试通过。
